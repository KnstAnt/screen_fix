# Protected Windows release inputs

The source archive is a development distribution. The ordinary Recorder remains available without the `elevated-release` feature.

Release engineering supplies `SCREEN_FIX_PUBLISHER_SPKI_SHA256` as exactly 64 lowercase hexadecimal characters encoding SHA-256 of the signing certificate's DER SubjectPublicKeyInfo. It supplies `SCREEN_FIX_RELEASE_ID` as exactly 32 lowercase hexadecimal characters encoding a unique, nonzero 128-bit ID for this complete payload. Use the same values for the Recorder, ordinary input helper and elevated collector x64 MSVC release targets, enabling `elevated-release` for each (with `--no-default-features`: the default development `dev-log` feature is rejected at compile time in a release build) and setting `-C target-feature=+crt-static` for the static C runtime. Sign all three images with the pinned key after the resources have been embedded. Protected attachment checks the whole signed set. The Recorder and standard helper declare asInvoker with UIAccess disabled. The standard helper uses the Recorder’s existing token and ordinary entry point. Standard capture under inherited administrator rights also works in a development build when the approved foreground meets the direct-access policy.

The WiX v4 authoring takes `Publisher`, a monotonically increasing three-part MSI `ProductVersion`, and the `Payload` directory containing the three exact image names in the authoring. Author the x64 package only. Release engineering checks startup imports against supported Windows system components, signs the completed MSI and publishes SHA-256 hashes of the signed MSI and three signed images. No user-writable plugin or external dependency directory is part of this payload.

The single mandatory feature installs machine-wide under `screen_fix` in the 64-bit Program Files known folder. Protected file and directory DACLs grant mutation to Administrators, SYSTEM and TrustedInstaller, while Users have read and execute access. The MSI manages transactional major upgrade and component removal from the same fixed directory. Stop the Recorder and its helpers before maintenance; held image guards can cause file-in-use handling while a launch is active. The application revalidates the installed paths, signer and release resource before protected attachment.

The protected launch requires the 64-bit Program Files directory on the local NTFS Windows installation volume. The launcher matches its DOS root to the global DOS mapping and the native volume of the operating system's loaded image, and holds the path and image guards through authentication. An Authenticode trust or cached revocation failure prevents attachment. All three files must bear the same release ID and trusted signer. The signed resource also identifies each image role, so swapping the filenames within a release set fails validation.

The running process image check uses the exact kernel-reported native path. Different spellings fail closed. The native path is reopened through the object-manager root and its volume, file ID and final path must match the held installed image. The source authoring leaves target collection disabled at attachment completion. Native registration and controller admission are separate stages.
